## 0. 阶段确认

Repository Owner 已决定：在 Phase 7 前插入 Phase 6.5，作为一次由开发者直接
主导的快速 Demo 优化阶段。

本阶段确认以下控制关系：

```text
开发者决定产品方向、范围、优先级和验收
    ↓
Agent 分析并执行开发者明确下达的有界任务
    ↓
聚焦验证与开发者手动 Demo 验收
    ↓
达到路演目标后再统一 Review / Audit / Freeze
```

Agent 不得自行把候选想法升级为当前任务，不得以“架构完善”“未来扩展”或“最佳
实践”为理由扩大范围。开发者对 Demo 的呈现方式、交互顺序、视觉取舍和任务优先级
拥有最终决定权。

正确性、安全、Secret 隔离、数据不破坏、真实状态和 Git 历史安全仍是硬边界，不能
以快速开发为理由绕过。

## 1. 为什么需要 P6.5

Phase 6 已冻结 Runtime 生命周期、微信/企业微信通道、配对、托盘、自启隐藏启动和
单实例等正式能力。Phase 7 的路线图目标是 Skills、MCP、备份恢复和 Runtime 升级，
不适合在路演前直接展开。

P6.5 的任务不是提前实现 Phase 7，而是：

- 将现有能力整理为容易理解和稳定演示的产品路径；
- 优化首次安装、启动、配置和演示过程中的明显摩擦；
- 完善路演所需的 UI、包装、提示、诊断和展示节奏；
- 快速吸收开发者现场提出的优化要求；
- 形成一个精确可识别的 Demo 构建和演示脚本。

P6.5 不移动、不覆盖也不重新解释 Phase 6 frozen tag。发现 Phase 6 回归时，应作为
明确回归修复处理，而不是修改历史审计或移动既有 tag。

## 2. 决策权与执行权

| 事项 | 最终决定者 | Agent 权限 |
| --- | --- | --- |
| Demo 产品方向和故事线 | 开发者 | 可提出建议，不得自行决定 |
| 功能是否进入 P6.5 | 开发者 | 只实现明确授权项 |
| UI、交互、文案和视觉优先级 | 开发者 | 按指令实现并报告明显可用性问题 |
| 是否使用现有未提交工作 | 开发者逐项确认 | 不得自动纳入、丢弃或改写 |
| 临时取舍是否可用于路演 | 开发者 | 必须说明影响，不得突破硬安全边界 |
| commit、push、merge、tag、发布 | 开发者明确授权 | 未授权时保持本地修改 |
| 测试范围 | 与变更风险相称；开发者可要求追加 | Agent 运行必要聚焦检查，避免重复未变化全量检查 |
| P6.5 最终通过和冻结 | 开发者 + 独立 Review/Audit | Agent 自己的完成总结不能替代最终审查 |

开发者的新指令可以调整尚未完成任务的优先级。若指令改变了已批准的范围或安全/
架构边界，应先在本文件的决策记录中补充一条简短变更，而不是让 Agent 静默扩大范围。

## 3. 快速开发工作方式

P6.5 采用快速、短反馈的开发节奏：

1. 开发者描述一个具体 Demo 问题或期望结果；
2. Agent 将其收敛为最小可交付修改；
3. 优先使用现有模块和设计，不为单一 Demo 场景建立通用框架；
4. 运行受影响的聚焦测试、类型检查或构建；
5. 开发者进行实际界面或完整 Demo 验收；
6. 通过后再进入下一个优化项；
7. 只在阶段里程碑运行一次适用的完整 Gate 和精确候选 CI。

本阶段明确避免：

- 每个小 UI 修改都重复运行未变化的完整 CI；
- 因理论风险增加没有真实调用者的接口、Manager、Repository 或插件框架；
- 为了“看起来更完整”提前实现 Phase 7 及更后阶段能力；
- 把低影响、不可复现的假设升级为阻断路演的 High；
- 为获得绿色结果而降低真实安全、正确性或数据完整性标准。

可复现的崩溃、错误成功状态、Secret/账号/二维码泄露、数据破坏、错误 Profile 操作、
安装失败和无法完成核心 Demo 路径仍必须优先修复。

## 4. P6.5 候选工作范围

以下是开发者可以逐项授权进入 P6.5 的工作类别，不代表全部自动获准：

### 4.1 路演安装与首次启动

- Windows Demo 安装包和首次启动体验；
- 安装来源、下载源和镜像选择的可演示性优化；
- 内置或受管前置依赖的 Demo 可靠性；
- 安装进度、失败提示、恢复入口和必要诊断；
- 降低路演机器环境差异导致的演示失败概率。

### 4.2 Demo UI 与产品叙事

- 首页、Runtime、Instance、模型和通道页面的视觉优化；
- 让关键状态、下一步操作和错误恢复更容易被现场观众理解；
- 精简路演路径中的无关信息和多余操作；
- 演示文案、本地化、空状态、加载状态和成功反馈；
- 不改变真实语义的布局、动效和品牌呈现优化。

### 4.3 端到端 Demo 可靠性

- 启动 YORVA；
- 识别或安装受支持的 Hermes；
- 创建或选择 Instance/Profile；
- 配置模型和本地输入凭据；
- 启动 Runtime 并展示权威状态；
- 按开发者确定的脚本连接微信/企业微信并展示通道状态；
- 展示托盘、隐藏启动、单实例和必要诊断；
- 在失败后以可理解方式恢复到可继续演示的状态。

### 4.4 Demo 包装与交付

- 精确 Demo 版本、commit、安装包和 SHA-256 记录；
- 路演机器准备清单；
- 脱敏 Demo 数据与演示脚本；
- 可回滚、可重新安装的 Demo 交付方式；
- 明确列出仅适用于 Demo 的限制。

```text
AMENDMENT        属于既有冻结阶段的正式修正，需要单独 Amendment / Audit
FUTURE           延后到 P7、P8 或更后阶段
```

Agent 在未获得标记前不得 reset、stash、删除、覆盖、移动、格式化或提交这些工作。
若不同类别的修改在同一文件中不可分离，应报告具体重叠，由开发者决定拆分方式。

## 6. 硬边界与默认非目标

除非开发者正式修改本阶段 Spec，并完成必要的架构/安全决策，P6.5 默认不包括：

- Skills、MCP、备份/恢复和通用 Hermes 升级能力；
- Phase 9 Control Plane、远程管理、组织或设备云端模型；
- Phase 10 RBAC、SSO、企业策略或私有部署；
- Phase 11 第二 Runtime、Runtime Marketplace 或动态插件 SDK；
- 任意 shell、进程、服务、注册表、文件系统或环境变量管理 API；
- 未经明确同意的遥测、账号数据收集或远程日志上传；
- 伪造 `RUNNING`、`CONNECTED`、安装成功或 Operation 成功状态；
- 把 Mock/演示数据混入正常产品模式而不做明显标记；
- 在日志、SQLite、事件、普通 API、截图或提交中保存 Secret、二维码、配对码、
  Token、Cookie 或账号标识；
- 重写 Git 历史、移动 Phase 6 tag 或删除失败审计；
- 为方便 Demo 关闭认证、放宽 CSP、静默提权或永久要求 Administrator/root。

如果开发者明确要求模拟演示，模拟数据必须处于独立、明显标记的 Demo 模式，且不能
让正常产品路径把模拟成功误认为真实 Runtime 或 Channel 成功。

## 7. Demo 验收路径

最终演示脚本和顺序由开发者确定。最低建议路径为：

```text
安装 / 启动 YORVA
→ 完成必要前置依赖
→ 识别或安装 Hermes
→ 创建或选择 Instance
→ 配置模型
→ Start 并展示权威 RUNNING
→ 连接开发者指定的 Channel
→ 展示 CONNECTED 与生命周期状态的区别
→ 展示托盘 / 隐藏启动 / 单实例
→ 展示一项开发者选择的核心价值场景
```

路演前至少形成：

- 一个开发者批准的演示故事线和操作脚本；
- 一个精确 commit/build/MSI 映射；
- 一次在目标 Windows 路演环境上的完整排练记录；
- 一次最终候选 CI；
- 一份不包含 Secret、二维码、配对码或账号信息的脱敏证据；
- 一份已知限制和现场恢复步骤。

不在开发者演示脚本中的能力不需要为了形式完整而强行现场展示，但不能将未验证的
能力写成已验证。

## 8. 验证策略

### 8.1 日常快速迭代

根据改动运行最小有效集合：

- React/TypeScript：相关测试、typecheck、lint；
- Go：受影响 package 测试，协议/迁移变更时增加对应测试；
- Rust/Tauri：相关单元测试、`cargo check`，原生行为变化时做 Windows smoke；
- OpenAPI：lint、generate 和 drift；
- 打包输入变化：构建并检查新的 MSI；
- UI-only 变化：开发者实际界面验收加相关组件测试。

不得重复运行没有代码或输入变化的绿色完整 Gate 来制造活动记录。

### 8.2 Demo 里程碑

在开发者宣布候选稳定后，执行一次适用的完整 Gate、精确候选 CI 和目标机器 Demo
排练。若之后只有文档变化，不重复构建 MSI；若可执行文件、资源、版本或打包输入
变化，则必须重新建立精确包映射。

- 具体开发分支由开发者指定；
- Agent 不得因本文件自动切换分支、提交、push、merge、tag 或发布；
- 每次提交只包含开发者已纳入 P6.5 的工作；
- 不得把相邻 Amendment、实验文件或个人临时产物混入 Demo baseline；

  `phase-0065-developer-led-demo-baseline`；

## 10. 阶段状态与退出规则

P6.5 使用既有阶段状态，但采用快速开发执行模式：

```text
DRAFT
→ READY（开发者确认首批任务）
→ IN_PROGRESS（开发者主导快速迭代）
→ AUDIT（Demo 功能冻结，仅允许审查修复）
→ PASSED / PASSED_WITH_CONDITIONS
→ FROZEN 或明确放弃合并
```

要将 P6.5 标记为 `COMPLETE / FROZEN`，至少需要：

- 开发者确认 Demo 目标已经达到；
- 精确候选和最终交付物可识别；
- 核心 Demo 路径通过；
- 没有未解决的 Critical、阻断 High 或真实 Secret/数据安全问题；
- 必要测试、目标环境 smoke 和 CI 通过；
- 独立 Review/Audit 给出可接受结论；
- 已知限制被如实记录；
- 开发者授权 commit、push、merge 和 annotated tag。

Phase 7 只能在 P6.5 被正式冻结，或开发者明确决定 P6.5 不合并并恢复到 Phase 6
frozen baseline 后开始。P6.5 的临时 Demo 取舍不能无记录地成为 Phase 7 的新默认。

## 11. 停止并交还开发者决定的条件

Agent 仅在出现下列实质问题时停止当前修改并报告：

- 发现 Secret、二维码、配对码、账号或 Token 进入持久/共享表面；
- 修改可能破坏或不可逆迁移用户数据；
- 真实 Runtime/Channel 状态会被伪造或错误归因到其他 Profile；
- 需要关闭认证、放宽安全边界、隐藏提权或引入任意系统控制面；
- 需要改变冻结 ADR/架构方向但尚无 Amendment；
- 现有开发者工作与任务无法安全分离；
- commit、push、merge、tag 或发布缺少开发者授权。

普通 UI 取舍、局部可维护性建议或无可复现影响的理论风险不应自动阻断快速 Demo
迭代；应简短说明后继续服从开发者决定。
