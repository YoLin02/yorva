# YORVA Local Data Model

## 1. Scope

This document defines the V0.1 SQLite model used by `yorvad`.

It does not define the future Control Plane PostgreSQL schema.

## 2. Ownership rule

SQLite stores **YORVA management state and metadata**.

It is not a shadow database of Hermes.

Hermes remains authoritative for Hermes-owned data such as sessions, memory, native profile configuration and native gateway state.

## 3. General conventions

- IDs: opaque text IDs generated by YORVA.
- timestamps: UTC RFC3339 at API boundary; database may store integer epoch milliseconds or normalized text consistently.
- booleans: integer 0/1 when required by SQLite.
- JSON metadata: use only for Runtime-specific or low-query metadata, not as a replacement for modeled columns.
- migrations: mandatory for every schema change.
- foreign keys: enabled.

## 4. `nodes`

Represents the local Node identity.

```text
id                TEXT PRIMARY KEY
name              TEXT NOT NULL
hostname          TEXT NOT NULL
platform          TEXT NOT NULL
architecture      TEXT NOT NULL
node_version      TEXT NOT NULL
created_at        ... NOT NULL
updated_at        ... NOT NULL
```

V0.1 typically contains one local row, but modeling Node explicitly avoids a destructive schema change when Cloud arrives.

Do not store Cloud auth secrets in this table.

## 5. `runtime_installations`

Represents a detected/managed Runtime installation.

Phase 3 creates this table and writes a row only after authoritative Phase 2 post-check succeeds for the managed official installation. Hermes remains authoritative; the row is last-known accepted metadata.

```text
id                TEXT PRIMARY KEY
node_id           TEXT NOT NULL REFERENCES nodes(id)
runtime_kind      TEXT NOT NULL
install_path      TEXT
version           TEXT
support_state     TEXT NOT NULL
status            TEXT NOT NULL
metadata_json     TEXT
last_detected_at  ...
created_at        ... NOT NULL
updated_at        ... NOT NULL
```

Constraint:

```text
UNIQUE(node_id, runtime_kind, install_path)
```

If a Runtime later supports multiple installation discovery semantics, update through an ADR/migration rather than over-generalizing V0.1.

## 6. `instances`

Normalized YORVA instance inventory.

```text
id                       TEXT PRIMARY KEY
runtime_installation_id  TEXT NOT NULL REFERENCES runtime_installations(id)
native_id                TEXT NOT NULL
name                     TEXT NOT NULL
is_default               INTEGER NOT NULL
is_protected             INTEGER NOT NULL
availability             TEXT NOT NULL  -- AVAILABLE | MISSING | UNKNOWN
last_synced_at           ...
created_at               ... NOT NULL
updated_at               ... NOT NULL
```

Constraint:

```text
UNIQUE(runtime_installation_id, native_id)
```

For Hermes, `native_id` is the adapter-owned identifier for the Hermes profile.

`status` is a normalized cached/last-known value. Runtime queries remain authoritative.

## 7. `operations`

Durable long-running management operations.

```text
id                 TEXT PRIMARY KEY
operation_type     TEXT NOT NULL
target_type        TEXT
target_id          TEXT
status             TEXT NOT NULL
stage              TEXT
progress           INTEGER
message            TEXT
error_code         TEXT
error_message      TEXT
retryable          INTEGER
idempotency_key    TEXT
correlation_id     TEXT
source_pin         TEXT  # Hermes install pin recorded at create; empty or mismatched pin never authorizes retry
ownership_nonce    TEXT  # unused by generation install retry; never returned by HTTP
transaction_id     TEXT  # one-way projection of InstallTransaction id; not an activation source
created_at         ... NOT NULL
started_at         ...
completed_at       ...
updated_at         ... NOT NULL
```

Indexes:

```text
(status, created_at)
(target_id, created_at)
UNIQUE(target_type, target_id) WHERE status IN ('PENDING', 'RUNNING')
  AND operation_type IN ('runtime.install', 'hermes.prerequisites')
```

If idempotency is used locally:

```text
UNIQUE(idempotency_key) WHERE idempotency_key IS NOT NULL
```

`transaction_id` is a one-way projection of the filesystem InstallTransaction. Recovery and retry authority is the transaction record and `active.json`, not this column. `ownership_nonce` is not generated for generation installs and must not authorize retry. HTTP Operation responses still omit nonce and secret material.

Generation install state lives in `control/transactions/txn_*.json` and `control/active.json`. Automatic GC follows D4 retention and never deletes unknown directories, legacy `hermes-agent`, or official Hermes user data.

Progress must be null when percentage has no meaningful interpretation. Do not invent fake percentages.

## 8. `operation_events`

Optional but useful for durable operation diagnostics/progress history.

```text
id              INTEGER PRIMARY KEY AUTOINCREMENT
operation_id    TEXT NOT NULL REFERENCES operations(id) ON DELETE CASCADE
sequence        INTEGER NOT NULL
event_type      TEXT NOT NULL
stage           TEXT
message         TEXT
metadata_json   TEXT
created_at      ... NOT NULL
```

Constraint:

```text
UNIQUE(operation_id, sequence)
```

Retention may be bounded later. This is not a general event-sourcing store.

## 9. `channel_bindings`

Stores safe metadata about an Instance channel connection.

```text
id             TEXT PRIMARY KEY
instance_id    TEXT NOT NULL REFERENCES instances(id) ON DELETE CASCADE
channel_type   TEXT NOT NULL
state          TEXT NOT NULL
account_label  TEXT
external_id    TEXT
metadata_json  TEXT
last_checked_at ...
created_at     ... NOT NULL
updated_at     ... NOT NULL
```

Constraint:

```text
UNIQUE(instance_id, channel_type, external_id)
```

If a Runtime/channel supports only one binding and has no stable external ID, the adapter/application may use an empty normalized external identity and enforce one active binding.

**No channel token or credential plaintext is stored here.**

## 10. `secret_refs`

Stores metadata/reference handles for secrets held by an OS secure store.

```text
id             TEXT PRIMARY KEY
scope_type     TEXT NOT NULL
scope_id       TEXT NOT NULL
secret_name    TEXT NOT NULL
provider       TEXT NOT NULL
provider_ref   TEXT NOT NULL
created_at     ... NOT NULL
updated_at     ... NOT NULL
```

Constraint:

```text
UNIQUE(scope_type, scope_id, secret_name)
```

`provider_ref` must not itself contain the secret.

## 11. `backups`

Stores backup metadata, not necessarily backup bytes.

```text
id             TEXT PRIMARY KEY
instance_id    TEXT NOT NULL REFERENCES instances(id)
kind           TEXT NOT NULL
path           TEXT NOT NULL
size_bytes     INTEGER
checksum       TEXT
runtime_version TEXT
status         TEXT NOT NULL
created_at     ... NOT NULL
```

Backup contents remain on local storage unless the user explicitly configures future remote storage.

## 12. `app_settings`

Small non-secret daemon settings.

```text
key            TEXT PRIMARY KEY
value_json     TEXT NOT NULL
updated_at     ... NOT NULL
```

Do not use this table for secrets or high-cardinality domain state.

## 13. `audit_log`

Security/management-relevant local actions.

```text
id              INTEGER PRIMARY KEY AUTOINCREMENT
action          TEXT NOT NULL
target_type     TEXT
target_id       TEXT
result          TEXT NOT NULL
actor_type      TEXT NOT NULL
actor_id        TEXT
correlation_id  TEXT
metadata_json   TEXT
created_at      ... NOT NULL
```

Never write secrets to `metadata_json`.

V0.1 audit is lightweight and local; it is not an enterprise compliance ledger.

## 14. What is intentionally not stored

Do not duplicate by default:

- Hermes conversations/sessions;
- Hermes memory;
- complete Hermes config files;
- API key plaintext;
- OAuth/channel token plaintext;
- QR codes after authentication;
- Phase 2 Hermes discovery responses or executable candidates;
- arbitrary Runtime logs forever.

## 15. Reconciliation behavior

On startup and explicit refresh:

1. detect Runtime installations;
2. query Runtime-native instances;
3. upsert normalized instance metadata;
4. update `last_synced_at`;
5. mark/remove stale rows according to reconciliation policy;
6. never delete Runtime-native data merely because YORVA metadata is missing.

## 16. Migration rules

- migration files are ordered and immutable after release;
- migration is tested from empty DB and previous supported schema;
- destructive changes require explicit data migration;
- backup critical local metadata before risky migration;
- schema version is not inferred from application version.
